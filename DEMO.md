# VaultLine Verify — synthetic demo

Every company, lender, invoice and claim below is **SYNTHETIC**. Recorded claims are assertions,
not proof of actual financing or legal rights. This demonstrates recorded VaultLine evidence only,
not global financing coverage. Authentication/authorization are not implemented; bind to localhost.

## Launch without contaminating existing records

Prerequisites: existing Python 3.12 API dependencies (`uv sync --dev` from `apps/api`), frontend
packages (`npm ci` from `apps/web`), and reachable PostgreSQL with CREATE SCHEMA permission.
Keep your existing backend database configuration. Do not reset PostgreSQL, change credentials,
copy over existing `.env` files, or stop unrelated services. Ports 8101 and 3100 must be free.

Terminal 1, from the repository root:

```bash
cd apps/api
uv run python scripts/demo.py
```

Terminal 2, from the repository root:

```bash
cd apps/web
NEXT_PUBLIC_API_BASE_URL=http://127.0.0.1:8101 VAULTLINE_NEXT_DIST_DIR=.next-demo npm run dev -- --hostname 127.0.0.1 --port 3100
```

Open **http://127.0.0.1:3100/cases**. The script seeds five cases through the real FastAPI endpoints,
extracts every document, records two claims, verifies all five cases and prints their detail paths.
It creates a unique PostgreSQL schema inside an uncommitted outer transaction, with no public
schema fallback. Request sessions use savepoints and serialize access to the shared connection.
Evidence files live in a private temporary directory. Existing cases and history cannot be selected
or modified by these request sessions. It applies existing migrations only inside this temporary
schema; it does not advance the user's Alembic version or add a new product migration.

Stop only these demo processes with Ctrl-C. The API rolls back the entire demo schema and closes
its temporary evidence directory. The next launch starts clean. A process crash closes the DB
connection and PostgreSQL rolls back the schema; temporary files may require ordinary OS cleanup.
Do not leave the transaction open indefinitely. This is a local demonstration harness, not a
production deployment or crash-durable store. Normal application persistence remains unchanged.

The runtime provider remains Meta. This isolated demo explicitly sets `allow_requests=False` on
its Meta adapter, before credentials are read or a network client is constructed. **No live AI
requests are made, even if a real key already exists in the environment.** No key, billing or
sharing settings need to change. No mock response is generated by the interactive demo.

## Reproduce the presentation

1. Open **SYNTHETIC Matching invoice and PO**. Both CSVs are already extracted. Click **View saved
   extraction** on each and open **Field provenance and original values**. Show invoice number,
   exact USD 1,000.00 total, PO reference, row locations and preserved original/normalized values.
2. Click **Run verification**. All applicable checks pass, including matching quantities/unit prices.
   Explain that passed document checks do not independently authenticate documents or legal rights.
   Run again, select an earlier **Historical run**, and show that saved results persist while this
   demo session remains open.
3. Open **SYNTHETIC Invoice exceeds PO**. Its invoice is USD 1,200.00 and unit price USD 600.00;
   the PO is USD 1,000.00 with unit price USD 500.00. Both extract cleanly: these are deliberate
   cross-document discrepancies, not malformed fixtures. Run verification and inspect **invoice
   total** and **line unit price**, including their source provenance.
4. Open **SYNTHETIC Potential conflict lender A**, then **… lender B**. Click **Load claims and
   conflicts**. Each case records an active USD 700.00 assertion for matching invoice evidence,
   from SYNTHETIC Lender Alpha or Beta. Show **Potential competing claims — investigate** and
   **Recorded active amounts exceed invoice total** (USD 1,400.00 against USD 1,000.00).
   Open supporting evidence. The document checks also flag the invoice number repeated across
   these two cases. Neither finding proves actual financing, fraud, ownership or enforceability.
5. Open **SYNTHETIC Missing evidence** and run verification. Show **Insufficient evidence** and
   the missing invoice/PO findings. Unknown evidence is never filled in with invented facts.
6. In **AI Investigation**, click **Start investigation**. The interactive offline demo saves a
   failed attempt showing **Live Meta requests are disabled for this demo. No provider call was
   made.** Load its history to show safe, auditable failure handling. Do not imply it is a successful
   Meta investigation. The account billing restriction remains a blocker for live Meta output.
7. Demonstrate successful structured investigation generation using the automated test command
   below. Only test applications explicitly inject `MockAIProvider`. Browser tests show a bold
   **TEST ONLY — deterministic mock investigation; no Meta response** label. Mock output is not
   evidence of Meta model quality or real provider availability.

To perform the uploads manually instead of starting with seeded cases:

```bash
cd apps/api
uv run python scripts/demo.py --empty
```

Use the same frontend command. Create synthetic cases, select **Invoice** or **Purchase order**
explicitly, and upload the corresponding files from `demo/synthetic/`. Extract both before
verification. For the two competing cases use the same conflict CSV pair, distinct lender names,
claim references `SYNTHETIC-conflict_a-claim` / `SYNTHETIC-conflict_b-claim`, amount `700.00`, currency
`USD`, status `active`. Create both claims before inspecting conflicts. Keep the clean matching
case separate: the shared conflict invoice intentionally triggers the dataset-wide duplicate rule.
The manifest is the authoritative map of files, claim inputs and expected outcomes.

## Feature 8: evidence-based risk assessment

On any case, click **Assess recorded evidence**. The matching case shows **No discrepancy found in
the recorded checks**, the mismatched and competing-claim cases show **Findings require human review**,
and the missing case shows **Insufficient evidence for complete recorded checks**. Every result keeps
**External financing remains unknown** and a human-review requirement visible. Expand a discrepancy
or conflict indicator to inspect its exact finding, claim IDs and available field provenance.
These are categorical recorded-evidence indicators, not credit predictions or financing decisions.
After changing/extracting documents, refresh the assessment; stale coverage asks for a new verification
run. The read-only assessment is independent of AI and changes no saved histories.

## Automated validation

From the repository root:

```bash
(cd apps/api && uv run pytest -q)
(cd apps/api && uv run ruff check src tests scripts && uv run ruff format --check src tests scripts)
(cd apps/web && npm run lint && npm run build)
```

Focused complete API workflow, including explicit mock investigation generation:

```bash
cd apps/api
uv run pytest tests/test_demo_workflow.py -v
```

Browser prerequisites and execution, from `apps/web`:

```bash
npm ci
npx playwright install chromium --no-shell
npm run test:e2e
```

Playwright starts its own loopback API on 8102 and frontend on 3101, refuses to reuse existing
servers and shuts down only its own processes. Keep both ports free. The browser API is a
**test-only** application: explicit MockAIProvider injection and a blocked external HTTP transport.
The browser also aborts non-loopback network requests. No live AI credentials are required.
Chromium must have its system libraries available; on a fresh Linux CI image install the
Playwright browser system dependencies through your normal approved system package workflow.
The frontend uses `.next-e2e`, separate from the normal `.next` build and `.next-demo`.

Browser coverage: case creation, explicit document typing, file upload, extraction, row provenance,
matching checks/history, deliberate discrepancies, two lenders/cases, potential conflicts,
structured test investigation, unknown/external-financing labels, history reload, case isolation,
and creating a new case while viewing a later list page. Backend tests also verify immutable
verification/investigation history and that the default provider stays Meta.

The current Meta smoke script must **not** be run while billing is restricted. It is not part of
any demo or test command above. No external AI request was used to validate this demo.

## Limits and remaining blockers

- Live Meta investigation is blocked by the account billing restriction. No billing/settings changes
  or live smoke requests are part of this task. Interactive offline demo shows the honest error;
  successful mock investigations are confined to tests.
- Supported sources are the documented field/value CSVs and text PDFs; no OCR/arbitrary layout parsing.
- Deterministic matching is conservative text/evidence comparison, not independently verified legal
  identity. Dataset-only conflict detection cannot exclude external financing.
- The rollback-only harness intentionally does not retain data after exit. Normal application history
  is persistent; the demo demonstrates history across HTTP requests and browser reloads, not restarts.
- No production authentication, authorization, global registry or automatic lending decision exists.
- AI investigation language is bounded, as described in `apps/api/INVESTIGATIONS.md`.
